# 前沿变化范围与观察候选缓存（2026-11-08）

## 已实现

1. 每批地图提交后，根据实际提交的成熟表面信息筛出前沿输入变化列，再检查本列及八邻列。尚未改变提交表面的点与纯代价变化不进入边界重判。
2. 未知前沿按切片、XY与实际表面高度增删；某层成熟不会清空该 XY 的其他层。
3. 高度变化先比较实际连接。连接未变时不重标连通分量；改变时只重标相关切片的 XY 地图块，在块内连通片图上处理完整簇的合并与分裂。
4. 建图写锁内不再立即搜索观察点。局部候选几何按需缓存，依赖同切片、局部地图块和前沿半径内的表面状态；查询时进行机器人距离、局部窗口、可达性与完成位置过滤。
5. 普通代价变化不重新聚簇；其他楼层或远处地图变化不直接清空所有候选缓存。
6. 空更新清零本轮前沿工作计时，避免把上次大更新的耗时反复报告成当前耗时。

完整流程与诊断字段见 [pct_frontiers.md](pct_frontiers.md)。安全判定、观察半径、最小观察距离、最终到达容差及原生 PCT/RDP 规划规则沿用现有设置。

## 验证

- 编译、安装完成。
- 8 项核心 CTest 和 7 项独立 ROS 域流程测试通过。前沿索引与窗口测试共 28 个用例。
- 成员集合与全量重建比较；连通结果另用独立的逐节点 BFS 校验。覆盖随机多层多批融合、跨块桥接的拆分与合并、同层代价变化、未成熟点、跨楼层缓存隔离、完成记录及机器人移动时的候选复用。
- 单点局部扩展示例：全簇共 820 个前沿层格，仅重判 9 列，重标 4 个切片块中的 132 个层格；连通图访问 24 个片。结果与完整重建一致。
- 独立 ROS 测试模拟执行回执，验证选点、层析规划、局部/全局后备、超时保持、脱困、地图发布与点云来源。它不是 Gazebo 行走或防摔测试。

## 离线耗时对照

使用同一份保存的 294229 个层格恢复索引输入，再对相同的局部已知格提交代价变化；前后前沿成员与聚簇结果一致。数值来自三次局部更新的中位数。

| 阶段 | 修改前 | 修改后 |
|---|---:|---:|
| 首次完整索引建立 | 8433 ms | 5741 ms |
| 首次局部查询（冷缓存） | 271 ms | 307 ms |
| 局部代价变化后的前沿维护 | 304 ms | 4.8 ms |
| 随后的局部查询 | 274 ms | 91 ms |

旧链路每次刷新 647 个簇；新链路不重建簇，只撤销 7 个相关局部候选缓存。首次查询仍可能承担候选构建工作，不能把写侧减少的耗时直接等同于每次控制决策都减少相同时间。

另用 16 帧保存的真实点云回放，前后最终成员和聚簇一致。小图与冷缓存情况下，候选查询并非每次都更快；该回放中前沿维护与查询合计从约 854 ms 降到 787 ms。不同地图规模、机器人位置和更新类型的结果需要分别看待。

本轮没有重启当前 Gazebo 实例，也没有用这些离线数值宣称原先 4.7～10.7 秒的等待已经消失。启动新进程后才会加载新模块；现场等待还包括 G/C、派生代价、显示组织与锁等待，需要后续跟踪确认。
